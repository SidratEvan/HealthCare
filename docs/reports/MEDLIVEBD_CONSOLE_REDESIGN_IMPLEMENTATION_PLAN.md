## 1. Executive summary

All eleven approved designs are feasible in the existing Next.js/React console, shared UI, shared domain, Express/Socket.IO and PostgreSQL architecture. Most changes concern layout, navigation, forms, confirmations and feedback. Do not ship eleven standalone HTML applications or their synthetic state machines. Keep existing services, deterministic domain rules, authentication, tenant boundaries, realtime reconciliation and offline stores underneath reusable React workspaces.

The clinical integration is more demanding than a visual replacement. Before real hospital use, protect doctor notes from queue changes; prevent a delayed doctor sign from completing the next patient's consultation; make walk-in creation and its queue event one guarded operation; close authentication/role gaps in socket access; and resolve patient-identity and clinician-access limits. Laboratory, Pharmacy and Import have additional privacy, validation or concurrency blockers before those modules handle real operational data.

Recommended order: shared console foundations and access safety → authentication/role landing → walk-in safety and Reception/Registration → doctor persistence/signing safety and Doctor → Administration/management → Ward/Emergency → Laboratory/Pharmacy → Platform onboarding/Import/National. Safety branches precede the affected visual branch. Existing administration setup remains available while the first workspaces are integrated; the first pilot need not wait for the entire eleven-workspace redesign.

There is no reason to add a UI framework, state-management framework, AI service or new national integration. Backend work is narrowly scoped to safety corrections, an authorised draft read, and an efficient administrative chamber overview. Custom follow-up, doctor queue lists, most role landing, Help, filters, confirmations and grouped settings do not justify new APIs.

### Extend what exists; scope the new appearance to consoles

`shared/ui/src/index.ts` already exports Button, Input, Card, Chip/FilterChip, Sheet, Toast, FreshnessLine, bed/capacity components, locale control and PrescriptionSheet. `Sheet.tsx` uses the existing Radix Dialog for focus containment/restoration and modal semantics. Keep those foundations, Tailwind v4, `@platform/i18n`, existing `next/font` Anek Bangla loading and existing domain/client packages. Avoid new dependencies.

Approved prototypes use a cool canvas/navy ink, clearer rectangular actions, fixed semantic status families and a compact rail. Production base tokens still describe warm green consoles (`shared/ui/src/tokens/tokens.css:13`), and some shared primitives also serve the already-approved patient app. Add an explicit console theme/root scope and console variants where needed; do not globally replace shared tokens and inadvertently recolour/restyle the patient app. Update affected token/contrast tests and reconcile design documentation within later authorised implementation branches. Map prototype brand shades onto existing hospital-derived brand variables; any extra presentational shade can be derived locally without adding hospital settings/schema fields.

### Interaction standards shared across all eleven workspaces

- **Navigation:** derive workspaces from authenticated roles and module configuration; these controls do not grant authority. Maintain compatibility with current query links and session refresh/logout. Choose a sole allowed workspace only after password/MFA gates. Persist last-work choice by account + hospital, never credentials or patient notes. A doctor without account linkage explicitly chooses a chamber by name; no guessed clinician binding.
- **Language:** one existing locale store and `t()` message dictionaries; contextual Help and every failure/confirmation must work in Bangla and English without resetting work. Format serials, money and time with existing i18n functions. Parse supported Bangla digits before numeric validation. Native date/file controls need bilingual instructions and a Dhaka-date summary, not a new date-picker package.
- **Controls:** distinguish status from action and selection; use native button/checkbox/radio/select semantics. Keep at least 44 px actionable touch targets, visible focus and AA text contrast. Status uses text/shape as well as colour. Hospital branding cannot recolour triage/clinical urgency.
- **Dialogs/Help:** reuse Radix Sheet/modal; name the action, patient/booking or bed/order, consequence and safe exit. No backdrop dismissal of destructive confirmations. Help should overlay without remounting the editor, disturbing focus or dropping a selected file. Restore focus on close; make panels/dialogs scroll within tablet height.
- **Errors and toasts:** inline field/action feedback is primary; toast is supplementary and must not cover active controls. Distinguish rejected, pending, committed and uncertain outcomes. “Saved” requires server acknowledgement/reconciliation; “queued offline” is not “saved to server”. Never fabricate clinical delivery guarantees from a successful local animation.
- **Loading/freshness:** retain the frame, brand and navigation; distinguish initial load, empty, unavailable, refresh failure and old data. Group common freshness captions but keep differing source ages visible. A refresh cannot renew a source's timestamp. Do not use zero for unavailable data.
- **Offline:** keep existing queued-action capabilities and stuck/retry/discard/durability warnings. Registration/serial issuance, private name reads, referral search and lab/pharmacy writes remain online where their current contracts require it. Doctor API draft/sign is not an offline outbox; keep unsent writing and label it accurately. Clinical note browser persistence would require explicit retention/security design; do not put notes into ordinary localStorage as a convenience.
- **Responsive:** compare against approved desktop 1440×900, tablet landscape 1024×768 and portrait 768×1024. Collapse rail and nonessential columns without hiding core actions; bound horizontal scrolling inside tables only when appropriate; keep patient identity and active queue target visible. Also check 200% text scaling, long Bangla names and larger lists.

## 4. Safety and correctness findings

**Critical** means resolve before the affected real hospital workflow is enabled. It does not mean every Priority 3/4 module must block a deliberately narrower Reception pilot. **Important** means address during that module's redesign. **Deferred** means separate scope/decision; no implied permission to implement it. Source observations are confirmed statically; race/failure scenarios need runtime regression tests in Phase 8B.
